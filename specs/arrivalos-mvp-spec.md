# ArrivalOS MVP Spec

Version: 0.2  
Status: Draft  
Last updated: 2026-05-25

## 1. Objective

ArrivalOS is a visibility and audit system for Gbèjà airport concierge arrivals.

The MVP should prove one core idea:

> A principal, watcher, concierge, and Gbèjà ops team can follow the same airport arrival through one trusted timeline, with WhatsApp updates delivered through Kapso.

The goal is not to build a full tracking platform first. The goal is to make the airport arrival process visible, calm, and auditable from flight approach to handover.

## 2. Product Principles

### 2.1 Core Product Shape

ArrivalOS is a trip timeline system.

The timeline is the source of truth. Every important action becomes a timestamped event:

- Flight approaching
- Concierge in position
- Flight landed
- Client met
- Checkpoint started
- Checkpoint completed
- Terminal exited
- Handover completed
- Trip completed

User interfaces, WhatsApp messages, receipts, and ops views are all projections of this timeline.

### 2.2 MVP Rule

A feature belongs in MVP only if it supports at least one of these jobs:

1. Identity certainty
2. Anxiety reduction
3. Distributed observation
4. Auditable proof

If a feature does not support one of these jobs, it is deferred.

## 3. Users And Roles

### 3.1 Principal

The arriving client or VIP.

Needs:

- Know who the concierge is.
- Know where to meet the concierge.
- Call the concierge quickly if needed.
- See basic trip progress after reconnecting.
- Log in or access their own client trip view, depending on the product surface.

### 3.2 Watcher

The spouse, executive assistant, family member, host company contact, or sponsor watching remotely.

Needs:

- Receive WhatsApp updates.
- Open a no-install web view.
- See current trip status.
- Know whether something is delayed.
- Avoid calling the principal or ops for routine updates.
- Log in or use limited-view access, depending on the invitation flow.

### 3.3 Concierge

The Gbèjà field operator handling the arrival.

Concierges do not have platform login accounts in MVP. They are operational records with public identifiers and trip-scoped update ability.

Needs:

- See assigned trip details.
- Confirm they are in position.
- Advance the trip through airport checkpoints.
- Record delays or notes.
- Complete handover.
- Continue working if airport network is unreliable.

Access rule:

- A concierge can update only trips assigned to their concierge record.
- Concierge update access should be granted through trip-scoped capability tokens or links.
- A concierge capability must not grant access to admin, watcher, or principal views.

### 3.4 Ops

The Gbèjà internal team monitoring active arrivals.

Needs:

- Log in as an admin or ops user.
- See all active trips.
- Identify stale or delayed trips.
- View trip timeline and notes.
- Follow up when a concierge has not updated the system.

## 4. MVP Scope

### 4.1 In Scope

- Trip creation
- Principal, watcher, concierge, and ops roles
- Login-capable admin, principal, and watcher accounts
- Trip-scoped concierge capability access
- Concierge mobile web workflow
- Principal mobile web view
- Ops active-trip dashboard
- Timeline event recording
- Kapso-powered WhatsApp outbound messages
- Email/SMS fallback for critical messages
- Basic offline queue for concierge actions
- Simple trip summary after completion

### 4.2 Out Of Scope For MVP

- Indoor geofencing
- Face matching
- Panic button
- Live vehicle tracking
- AI anomaly detection
- Dynamic checkpoint prediction
- Corporate analytics dashboard
- Multi-language interface
- Cryptographic hash-chained timeline
- WhatsApp inbound command processing

These are deferred deliberately. They may be valuable later, but they increase complexity before the core timeline loop has been proven.

## 5. System Of Record

ArrivalOS owns trip state.

WhatsApp does not own trip state. Kapso and WhatsApp are delivery channels for updates generated by ArrivalOS.

Correct flow:

```text
Concierge taps "Client met"
ArrivalOS records timeline event
ArrivalOS updates active trip state
ArrivalOS sends WhatsApp message through Kapso
Watcher receives update
```

Avoid in MVP:

```text
Concierge sends freeform WhatsApp message
ArrivalOS guesses intended state
ArrivalOS updates trip
```

The second flow depends on message parsing and creates avoidable ambiguity.

## 6. Identity And Access Model

### 6.1 Account Types

The people who can log in are:

| Account Type | Purpose | Scope |
| --- | --- | --- |
| Admin | Gbèjà internal administration and ops control. | Full operational access according to role. |
| Principal | Client-side access for their own trips. | Trips where they are attached as a principal. |
| Watcher | Limited remote visibility. | Trips they are invited to watch. |

Concierges are not login users in MVP.

### 6.2 Concierge Access

A concierge is a public operational actor, not an authenticated account.

Concierge records include:

- Name
- Phone
- Photo
- Public ID
- Active/inactive status

Concierge state updates should be authorized by a trip-scoped capability, not by a reusable user login.

Example:

```text
Concierge opens assigned trip link
ArrivalOS validates concierge public ID + trip capability token
Concierge can submit allowed timeline events for that trip only
Capability expires or is revoked when trip is completed/cancelled
```

This keeps field operations lightweight while limiting blast radius if a link is exposed.

### 6.3 Principal And Watcher Access

Principals and watchers are customer-side users with limited visibility.

Rules:

- A principal can view only trips where their user account is linked to a trip principal.
- A watcher can view only trips where their user account is linked to a watcher assignment.
- Neither principals nor watchers can mutate operational trip state.
- Principal and watcher views must expose only customer-safe timeline information.

### 6.4 Admin Access

Admins can:

- Create trips
- Add principals
- Add watchers
- Assign concierges
- Cancel trips
- View operational notes
- Review notification attempts

Admin actions should be recorded as timeline events or audit events where relevant.

## 7. Trip State Machine

### 7.1 States

| State | Meaning |
| --- | --- |
| `created` | Trip exists but active monitoring has not started. |
| `flight_approaching` | Flight is close to arrival. |
| `concierge_in_position` | Concierge has confirmed arrival-point readiness. |
| `flight_landed` | Flight has landed. |
| `client_met` | Principal and concierge have linked up. |
| `processing` | Principal is moving through airport checkpoints. |
| `terminal_exited` | Airport processing is complete. |
| `handover_completed` | Principal has been handed to driver or receiving party. |
| `completed` | Trip is closed and summary is available. |
| `cancelled` | Trip will no longer proceed. |

### 7.2 MVP Events

| Event | Actor | Resulting State |
| --- | --- | --- |
| `trip.created` | Ops | `created` |
| `flight.approaching` | System | `flight_approaching` |
| `concierge.in_position` | Concierge | `concierge_in_position` |
| `flight.landed` | System | `flight_landed` |
| `client.met` | Concierge | `client_met` |
| `checkpoint.started` | Concierge | `processing` |
| `checkpoint.completed` | Concierge | `processing` |
| `terminal.exited` | Concierge | `terminal_exited` |
| `handover.completed` | Concierge | `handover_completed` |
| `trip.completed` | System or Ops | `completed` |
| `trip.cancelled` | Ops | `cancelled` |

### 7.3 Checkpoints

The MVP checkpoint list should be configurable, but the default Nigerian arrivals flow is:

1. Port Health
2. DSS
3. Immigration
4. Baggage Claim
5. Customs
6. NDLEA
7. Quarantine

NDLEA and Quarantine may be skipped when not applicable, but skipped checkpoints should still be represented as skipped, not deleted from the trip history.

## 8. Required Screens

### 8.1 Concierge Trip Screen

Primary purpose:

Let the concierge advance the trip with minimal friction.

Must show:

- Principal name and photo
- Flight number and arrival airport
- Current trip state
- Current checkpoint
- Watcher count
- Offline sync status
- Primary action button
- Add note action
- Report delay action

Primary actions should change based on state:

| State | Primary Action |
| --- | --- |
| `created` or `flight_approaching` | Mark In Position |
| `flight_landed` | Mark Client Met |
| `client_met` | Start First Checkpoint |
| `processing` | Complete Current Checkpoint / Start Next |
| `terminal_exited` | Complete Handover |
| `handover_completed` | Close Trip |

### 8.2 Principal View

Primary purpose:

Give the principal identity certainty and simple meeting instructions.

Must show:

- Concierge name
- Concierge photo
- Concierge phone number
- Meeting point instructions
- Current trip status
- Call concierge button

The principal view should stay simple. It should not expose ops data, internal notes, or detailed audit information.

### 8.3 Watcher View

Primary purpose:

Reduce anxiety by showing trusted progress without requiring calls.

Must show:

- Principal name
- Current trip status
- Concierge name and photo
- Timeline feed
- Last updated time
- Delay notice if relevant

Watchers should not have operational controls in MVP.

### 8.4 Ops Dashboard

Primary purpose:

Help Gbèjà monitor active arrivals.

Must show:

- Active trips
- Principal name
- Airport
- Flight number
- Concierge
- Current state
- Last timeline event
- Last update time
- Delay flag

Ops can open a trip detail view to see all timeline events and notes.

## 9. WhatsApp Via Kapso

### 9.1 Channel Decision

WhatsApp is an MVP channel. Kapso is the provider.

ArrivalOS should integrate with Kapso rather than directly with the WhatsApp Business API.

Reason:

- Lower implementation complexity
- Faster setup
- Better developer experience
- Avoid direct Meta API operational overhead during MVP

### 9.2 Outbound MVP Messages

ArrivalOS should send WhatsApp messages through Kapso for:

| Trigger | Recipient |
| --- | --- |
| Trip created / watcher invited | Watcher |
| Flight approaching | Watcher |
| Concierge in position | Principal and watcher |
| Flight landed | Watcher |
| Client met | Watcher |
| Checkpoint delay | Watcher and ops |
| Handover completed | Watcher |
| Trip summary ready | Principal and watcher |

### 9.3 Fallback Channels

Use SMS or email fallback for critical messages only:

- Concierge in position
- Client met
- Handover completed

Fallback should be used when Kapso delivery fails or when the recipient has no confirmed WhatsApp delivery route.

### 9.4 Inbound WhatsApp

Inbound WhatsApp commands are out of scope for MVP.

Examples of deferred inbound commands:

- "Where is he?"
- "Mute updates"
- "Share trip"
- "Call concierge"

These can be added after the outbound timeline workflow is reliable.

## 10. Data Model Draft

### 10.1 Trip

Stores the arrival being managed. A trip is the operational container for one airport arrival timeline, not a single passenger record.

Fields:

- `id`
- `flight_number`
- `arrival_airport`
- `arrival_terminal`
- `scheduled_arrival_at`
- `actual_arrival_at`
- `status`
- `assigned_concierge_id`
- `created_at`
- `updated_at`

### 10.2 Trip Principal

Stores the passengers or protected people attached to a trip.

This supports cases where a family, delegation, or executive team arrives together under one concierge workflow.

Fields:

- `id`
- `trip_id`
- `user_account_id`
- `full_name`
- `phone`
- `photo_url`
- `primary_contact`
- `sequence_number`
- `created_at`
- `updated_at`

### 10.3 Watcher

Stores watcher assignments for people allowed to observe a trip.

Fields:

- `id`
- `trip_id`
- `user_account_id`
- `notification_channel`
- `created_at`

### 10.4 Concierge

Stores Gbèjà field operators.

Fields:

- `id`
- `full_name`
- `phone`
- `photo_url`
- `public_id`
- `active`
- `created_at`

### 10.5 User Account

Stores login-capable users only.

Concierges are intentionally excluded from this table in MVP.

Fields:

- `id`
- `full_name`
- `email`
- `phone`
- `password_hash`
- `account_type`
- `active`
- `created_at`
- `updated_at`

Allowed account types:

- `ADMIN`
- `PRINCIPAL`
- `WATCHER`

### 10.6 Concierge Trip Access

Stores trip-scoped update capability for a concierge.

Fields:

- `id`
- `trip_id`
- `concierge_id`
- `token_hash`
- `expires_at`
- `revoked_at`

### 10.7 Timeline Event

Stores the audit trail.

Fields:

- `checkpoint_name`

### 10.8 Notification

Stores outbound message attempts.

Fields:

- `created_at`

## 11. API Draft

### 11.1 Auth APIs

```text
POST /api/auth/register/admin
POST /api/auth/register/principal
POST /api/auth/register/watcher
POST /api/auth/login
POST /api/auth/refresh
POST /api/auth/logout
POST /api/auth/verify-email
POST /api/auth/verify-email/resend
POST /api/auth/password/forgot
POST /api/auth/password/reset
GET /api/auth/me
```

There is intentionally no concierge registration or login route.

Successful registration and login return:

- A JWT access bearer token
- A JWT refresh token
- Access and refresh expiry timestamps
- The authenticated user's profile

Access tokens must embed role/account-type claims so downstream authorization can distinguish `ADMIN`, `PRINCIPAL`, and `WATCHER`.

Refresh tokens are also JWTs, but ArrivalOS stores their hashes server-side so refresh sessions can be rotated and revoked.

Email verification is required before login. Password reset uses one-time, hashed reset tokens. Logout revokes the current access token and the supplied refresh token.

### 11.2 Standard API Error Contract

All API errors should return a stable object rather than anonymous maps.

Shape:

```json
{
  "timestamp": "2026-05-25T12:00:00Z",
  "status": 400,
  "code": "VALIDATION_FAILED",
  "message": "Validation failed",
  "path": "/api/auth/register/principal",
  "requestId": "6d3f2d94-8d95-40a4-90aa-25f31a7e02d6",
  "fieldErrors": [
    {
      "field": "email",
      "message": "must be a well-formed email address"
    }
  ]
}
```

Rules:

- `code` is the frontend branching key.
- `message` is display-safe copy.
- `fieldErrors` is present for form validation problems.
- `path` identifies the endpoint that failed.
- `requestId` should use `X-Request-Id` when provided, otherwise the API may generate one.
- Future domain exceptions should provide explicit error codes rather than deriving codes from exception messages.

### 11.3 Admin APIs

```text
POST /api/admin/trips
GET /api/admin/trips/active
GET /api/admin/trips/{tripId}
POST /api/admin/trips/{tripId}/principals
POST /api/admin/trips/{tripId}/watchers
POST /api/admin/trips/{tripId}/assign-concierge
POST /api/admin/trips/{tripId}/cancel
```

### 11.4 Concierge Capability APIs

```text
GET /api/concierge-access/{token}/trip
POST /api/concierge-access/{token}/events
POST /api/concierge-access/{token}/notes
```

These endpoints are not login-protected by user accounts. They must validate the token hash, concierge assignment, expiry, revoked status, and trip status before accepting updates.

### 11.5 Principal APIs

```text
GET /api/principal/trips
GET /api/principal/trips/{tripId}
GET /api/principal/trips/{tripId}/timeline
```

### 11.6 Watcher APIs

```text
GET /api/watcher/trips
GET /api/watcher/trips/{tripId}
GET /api/watcher/trips/{tripId}/timeline
```

### 11.7 Kapso Webhook APIs

```text
POST /api/webhooks/kapso
```

The webhook endpoint should verify Kapso signatures before accepting events.

## 12. Non-Functional Requirements

### 12.1 Reliability

- Concierge actions should be queued locally when offline.
- Concierge capability tokens should tolerate retry/idempotency for queued actions.
- Duplicate event submissions should be idempotent.
- Notification failures should not block timeline event creation.

### 12.2 Security

- Principal and watcher accounts must be limited to customer-safe trip data.
- Concierge trip capabilities must use unguessable tokens.
- Store token hashes, not raw tokens.
- Store refresh token hashes server-side so JWT refresh tokens can still be revoked.
- Revoke access tokens on logout by token ID until their natural expiry.
- Reject tokens issued before `password_changed_at`.
- Require verified email before login.
- Concierge capability tokens must be revocable and expire after trip completion.
- Principal and watcher views must expose only customer-safe data.
- Admin routes must require authentication.

### 12.3 Auditability

- Timeline events should be append-only in normal operation.
- Corrections should be new events or admin-only edits with a reason.
- Every event should record actor, time, and source metadata.

### 12.4 Maintainability

- Keep WhatsApp provider logic behind a notification service interface.
- Avoid spreading Kapso API calls across controllers.
- Keep trip state transitions explicit and tested.

## 13. MVP Build Order

Completed foundation:

1. Spring Boot project setup with Postgres runtime, H2 tests, Flyway migrations, Spring Security, and startup tests.
2. Trip and timeline data model with entities, repositories, and migrations.
3. Login-capable user accounts for admins, principals, and watchers.
4. JWT bearer and refresh token lifecycle with rotation and revocation.
5. Logout, email verification, password reset, local MailDev support, Resend production sender, and standard API error object.

Next backend build order:

1. Trip state transition service.
2. Admin trip creation and assignment APIs.
3. Concierge trip capability issue/validate flow.
4. Concierge event capture API with idempotency.
5. Principal and watcher limited trip views.
6. Kapso outbound WhatsApp notification service.
7. Notification attempt tracking and delivery webhook handling.
8. Offline concierge event queue.
9. Trip summary generation.

## 14. Deferred Feature Parking Lot

These features are intentionally parked until after MVP:

- Indoor proximity alerts
- Browser geolocation
- Live vehicle pin
- Panic button
- WhatsApp inbound commands
- Dynamic ETA model
- Corporate analytics dashboard
- Multi-language UI
- Face verification
- Cryptographic event hash chain

Each deferred feature should require a short decision note before being added back into scope.
